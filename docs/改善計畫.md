# 改善計畫：幣安廣場內容助手

## 這個專案在做什麼（白話）

這個專案幫使用者整理行情、寫幣安廣場短文，再檢查文字。
它是給 Claude Code 或能讀懂操作說明的 AI 助手使用。
行情腳本會整理主流幣、漲跌榜與成交額。
文字檢查會看字數、標籤、繁體用字，以及容易像罐頭文章的句型。

發文腳本會先檢查草稿、每日篇數，再交給幣安官方工具發送。
真正發文需要使用者同意與自己的憑證。
這次不代發任何文章，也不改變同意後才發文的流程。
我們優先補上「出錯時先停下來」的保護。

## 可以運用的現成輪子

「輪子」是現成且有人維護的工具，不必每個功能都自己重寫。
本專案維持輕量：不新增執行時套件。

| 現在自己寫的部分 | 建議的成熟工具 | 裁決 | 理由 |
|---|---|---|---|
| 行情請求沒有明確等待上限 | AbortSignal.timeout（Node 內建） | 採用 | 設定 15 秒上限，避免請求一直掛著，不需安裝套件。 |
| 自己判斷要列出幾筆 | Number.isSafeInteger（內建） | 採用 | 排除零、負數、小數與過大數字，維持簡單。 |
| 手動執行測試 | node:test、node:assert（內建） | 採用 | 沿用現有測試，不用另外安裝測試框架。 |
| 自己做繁簡轉換 | OpenCC（既有工具） | 採用 | 沿用成熟轉換工具，不自行建立字表。 |
| 每次修改靠人記得驗證 | GitHub Actions | 採用 | 自動安裝 OpenCC 並跑離線測試，不使用發文憑證。 |
| 用規則拆解草稿狀態欄位 | gray-matter | 借鏡 | 完整處理前置資料較可靠，但會新增套件；本次只補最小擋錯。 |
| 自己檢查 API 回應欄位 | Zod | 借鏡 | 結構驗證有價值，但目前欄位少；不為此加入整個套件。 |
| 自己做重試與併發鎖 | p-retry、proper-lockfile | 不做 | 本次不擴充重試或發文併發機制，也不新增依賴，列為後續評估。 |

輪子不只指外部套件，執行環境內建的功能通常更適合小腳本。
這次採用內建工具，避免使用者多一串安裝步驟。

## 優化路線

### 本次 PR 已做

1. 行情請求加上 15 秒等待上限。
   連線失敗或逾時時，用清楚訊息結束，不再只留下難讀的錯誤。
2. 檢查行情資料格式。
   預期收到清單，而且每筆都有代號、價格、漲跌幅、成交額。
   欄位缺少或不是有效數字時先停止，不輸出看似正常的榜單。
   空清單仍可正常輸出空榜單。
3. 檢查 `--top` 的值。
   只接受正整數；沒有填值、零、負數、小數都會提供提示。
   沒有指定時，仍預設列出五筆。
4. 草稿沒有有效的 `status:` 狀態行就停止。
   這個檢查在文字檢查、讀憑證與呼叫官方發文工具之前。
   避免文章發出去了，卻沒有正確留下發文紀錄。
   空白狀態也視為資料不完整，請先填上 `status: draft`。
5. 補上不連網的安全測試。
   行情測試用假回應，不打幣安 API。
   發文測試只走提早拒絕的路徑，不使用憑證、不發文。
6. README 改用適合 Node 22 的測試指令。
   GitHub Actions 也固定使用 Node 22 並安裝 OpenCC。

### 之後可做（依價值排序）

1. 防止同時執行兩次發文。
   現有每日上限與已發文判斷不是鎖，仍有同時通過的可能。
   可先評估作業系統提供的鎖或單一發文排程，不急著裝新套件。
2. 提高發文後紀錄的可靠性。
   尤其要測試「幣安成功，但本機儲存失敗」。
   不能盲目重試發文，否則可能重複貼文。
3. 統一草稿前置資料的讀寫規則。
   先界定格式，再評估 gray-matter 的安裝成本是否值得。
   本次的狀態行檢查不是完整的 YAML 驗證器。
4. 固定官方發文工具的版本。
   避免重新安裝時，官方更新讓行為悄悄改變。
5. 依 HTTP 狀態分類行情失敗。
   限流時才考慮等待重試；格式錯誤不應一直重打。

## 怎麼確認這次沒有弄壞

先準備 Node 與 OpenCC。
執行 `node --test 'test/*.test.mjs'`。
測試不需要幣安憑證，也不應產生貼文。
自動測試不等於已驗證幣安實際服務；本次不做真實發文驗收。
